# Gコード（G-code）の基礎とバージョニング

Gコードは、CNC工作機械や3Dプリンターを制御するための数値制御（NC）言語です。DXFから加工機へのデータフローを理解する上で、Gコードの基礎知識は重要です。

---

## 1. Gコードとは何か？

### 1.1 基本概念

**Gコード（G-code）**は、工作機械に「工具をどこに動かすか」「どの速度で動かすか」などの加工命令を伝えるためのプログラミング言語です。

**主な特徴**:
- **逐次実行**: プログラムは上から順番に実行される
- **低レベル**: 座標移動、主軸回転、冷却液ON/OFFなどの具体的な動作を指定
- **機械制御に直結**: CADの「設計データ」とは異なり、「加工命令」そのもの

### 1.2 DXFとの関係

```
CAD (設計) → DXF (データ交換) → CAM (変換) → Gコード (加工命令) → CNC機械 (実行)
```

- **DXF**: 「何を書きたいか」を表現（形状の定義）
- **Gコード**: 「どう動かすか」を表現（工具の動作命令）

## 2. Gコードの歴史とバージョニング

### 2.1 標準化の歴史

G-codeの標準化は、1960年代から始まりました。

| 年 | 標準 | 説明 |
| :--- | :--- | :--- |
| **1963** | **RS-274** | EIA（Electronic Industries Association）が最初の標準を発表 |
| **1974** | **RS-274-B / RS-274-C** | 輪郭制御や位置決めの定義を統合・改善 |
| **1980** | **RS-274-D** | EIAによる最終版。可変ブロック形式、アドレス語（G、M、X、Y、Z等）、モーダルグループなどを正式化 |
| **1982** | **ISO 6983-1:1982** | RS-274DをISO標準化。国際標準として採用 |
| **2009** | **ISO 6983-1:2009** | 現在の標準版。構造の再編成、アドレスインデックス、新しい補間方法の追加 |

### 2.2 RS-274-D（EIA標準）

**RS-274-D**は、EIAが1980年に発表したG-codeの標準規格です。現在でも多くのCNCコントローラーがこの標準をベースにしています。

**主な特徴**:
- **可変ブロック形式**: 1行（ブロック）に複数の命令を含められる
- **アドレス語**: G（準備機能）、M（補助機能）、X/Y/Z（座標）など
- **モーダルコマンド**: 一度設定すると、変更されるまで有効なコマンド
- **補間タイプ**: 線形（G01）、円弧（G02/G03）など

### 2.3 ISO 6983（国際標準）

**ISO 6983**は、RS-274を国際標準化したものです。

**ISO 6983-1:1982**:
- RS-274Dとほぼ同等
- プログラム形式、アドレス語などの規則を定義

**ISO 6983-1:2009**（現在の標準）:
- 構造の再編成と論理的な流れの改善
- 準備機能（Gコード）と補助機能（Mコード）を1つの附属書に統合
- **アドレスインデックス**の導入（例：`X1=`, `X2=`で複数の軸グループを指定可能）
- 新しいプログラミング方法の追加：
  - ヘリカル補間（螺旋補間）
  - ねじ切り
  - ドウェル時間（待機時間）

**現在の状況**（2025年）:
- ISO 6983-1:2009が現在の標準版
- 1982年版は2009年版に置き換えられた（Revised by ISO 6983-1:2009）
- 実務上は2009年版を使用すべき

### 2.4 将来の標準：STEP-NC（ISO 14649 / AP-238）

**STEP-NC**は、G-codeの限界を克服するために開発された新しい標準です。

**G-codeの限界**:
- 軸の動きのみを伝達し、**高レベルのプロセス情報や特徴情報を持たない**
- メーカーごとに方言が異なり、互換性が限定的

**STEP-NCの特徴**:
- **特徴ベース**: 高レベルの加工特徴（穴、ポケット等）を表現
- **オブジェクト指向**: より豊富なデータモデル
- **ISO 10303（STEP）との統合**: CAD/CAM/CNCの統合を改善

**現状**:
- 2003年からISO 14649の各パートが公開開始
- 2005-2008年にSTEP-NCフレームワークが確立
- **採用は遅い**: 既存のRS-274コントローラーの基盤が大きく、ツールチェーン全体のサポートが必要なため

## 3. メーカー間の方言と互換性

### 3.1 標準と方言の問題

**重要な事実**: ISO 6983やRS-274-Dは標準規格ですが、**各CNCメーカーは独自の拡張機能を追加**しています。

**方言が生まれる理由**:
- メーカー独自の機能を追加したい
- 競合他社との差別化
- ユーザーの要望に対応

**結果**:
- 同じ標準をベースにしていても、**メーカー間で互換性が完全ではない**
- ある機械用に書かれたG-codeプログラムが、別の機械で正しく動作しないことがある

### 3.2 主要メーカーの特徴

#### Fanuc（ファナック）

**特徴**:
- 最も広く使用されているCNCコントローラー
- ISO標準に準拠した基本構文
- 強力なマクロ機能（`#変数`、IF/THENロジック等）

**主なGコード**:
- `G01`: 線形補間
- `G02/G03`: 円弧補間
- `G81`: ドリルサイクル
- `G84`: タッピングサイクル
- `G06.1`: スプライン補間（オプション）
- `G06.2`: NURBS補間（オプション）

**拡張機能**:
- 変数ベースのマクロ（`#100`, `#101`等）
- サブプログラム（`M98`, `M99`）
- 工具長補正（`G43/H`）

#### Siemens（シーメンス）Sinumerik

**特徴**:
- 2つのモード：ISOモードまたは「ShopMill / ShopTurn」モード
- 構造化されたプログラム
- 5軸加工や高速サイクルに強力

**主な特徴**:
- サイクル関数が`CYCLExx(...)`構文を使用
- R変数やシステム変数（`$AA_IM[...]`等）
- 構造化された制御ロジック、ラベルとコール

**拡張機能**:
- `CYCLE82`: ドリリング
- `CYCLE83`: ピークドリリング（Peck Drilling、ペックドリリング）
- 工具呼び出し: `TOOL CALL 1 Z S=5000`

#### Heidenhain（ハイデンハイン）

**特徴**:
- 主に会話型プログラミング（`CYCL DEF ...`形式）
- ISOモードもサポート
- 高精度、表面仕上げに優れる

**主な特徴**:
- `CYCL DEF 200 DRILLING`: ドリリング定義
- `CYCL DEF 205 PECK DRILLING`: ピークドリリング（Peck Drilling、ペックドリリング）
- `CYCL DEF 207 TAPPING`: タッピング
- FN関数、ラベル/コールスキーム（`LBL`, `CALL LBL`）

### 3.3 互換性の問題

**よくある問題**:

1. **サポートされていないサイクル**:
   - Fanucの`G83`（ピークドリリング、Peck Drilling）が、SiemensやHeidenhainでは異なる構文や動作

2. **マクロ言語の違い**:
   - Fanucの`#変数`が、SiemensやHeidenhainでは異なる構文

3. **会話型 vs 生G-code**:
   - Heidenhainは会話型プログラミングを推奨
   - ISOモードでも、フォーマットの期待値が異なる場合がある

4. **行番号とブロック形式**:
   - Siemensはラベル付きサブプログラムや特定のブロック構造を重視
   - Fanucはより柔軟

5. **工具オフセット、カッター補正、送り単位**:
   - 送り/分（G94）vs 送り/回転（G95）
   - 円弧の定義（IJK vs R）が異なる場合がある

### 4.3 座標軸

| 軸 | 説明 |
| :--- | :--- |
| **X, Y, Z** | 直線軸（通常はX=左右、Y=前後、Z=上下） |
| **A, B, C** | 回転軸（通常はA=X軸回り、B=Y軸回り、C=Z軸回り） |
| **U, V, W** | 第2直線軸（工具オフセット用など） |

### 4.4 安全面への警告：G-codeは物理的な機械を動かします

::: warning ⚠️ 重要：安全第一

G-codeは**物理的な機械を制御する**ため、プログラミングエラーが**機械の破損や人身事故**につながる可能性があります。特に以下の点に注意してください。

#### G00（早送り）の危険性

**G00は工具を最高速度で移動**させるため、設定ミスや座標系の取り違えにより、工具がワークや機械に**激突する**リスクがあります。

**主な危険要因**:
- **座標系の取り違え**（G54 vs G92等）は特に危険
- **CAMソフトの設定ミス**により、意図しない位置に工具が移動する可能性がある
- **単位の取り違え**（インチ vs ミリメートル）により、工具が予想外の位置に移動
- **Z軸の深さ設定ミス**により、工具がワークに突き刺さる

**実際の事故例**:
- 座標系の設定ミスにより、工具がワークに激突し、工具が破損
- Z軸の深さ設定ミスにより、工具がワークに突き刺さり、機械が損傷
- 単位の取り違えにより、工具が予想外の位置に移動し、ワークが破損

#### 必須の安全対策

1. **ドライラン（空運転）の実施**:
   - 実際の加工前に、**工具をワークから離した状態でプログラムを実行**し、動作を確認
   - 工具がワークに接触しないことを確認
   - 工具パスが意図した通りであることを確認

2. **シミュレーターの使用**:
   - CAMソフトのシミュレーター機能で、工具パスを事前に確認
   - 衝突検出機能を使用して、工具とワークの衝突を事前に検出

3. **段階的な実行**:
   - 最初は低い送り速度で実行し、問題がないことを確認してから本番速度に上げる
   - 特に新しいプログラムや変更したプログラムでは必須

4. **緊急停止ボタンの確認**:
   - 常に緊急停止ボタンの位置を確認し、すぐに押せる状態にする
   - 異常を感じた場合は、すぐに緊急停止ボタンを押す

5. **座標系の確認**:
   - G54-G59やG92の設定が正しいか、必ず確認
   - ワーク座標系の原点設定が正しいか確認

#### よくある危険なミス

| ミスの種類 | 危険性 | 対策 |
| :--- | :--- | :--- |
| **単位の取り違え** | インチとミリメートルの混同により、工具が予想外の位置に移動 | G20/G21の確認、プログラム冒頭での単位指定を確認 |
| **座標系の取り違え** | G54とG92の混同により、工具が間違った位置に移動 | 座標系の設定を確認、プログラム冒頭での座標系指定を確認 |
| **Z軸の深さ設定ミス** | 工具がワークに突き刺さる | Z軸の深さ設定を確認、段階的に深さを増やす |
| **工具径補正の設定ミス** | 工具がワークに食い込む | G40/G41/G42の設定を確認、工具径の設定を確認 |

#### 実務での推奨事項

**新しいプログラムの場合**:
- 必ず**ドライランで確認**してから実際の加工を開始
- 最初の数行だけを実行して、動作を確認
- 問題がないことを確認してから、全体を実行

**既存プログラムの変更時**:
- **変更箇所を特定**し、その部分を重点的に確認
- 変更前後のプログラムを比較して、意図しない変更がないか確認
- 変更箇所だけでなく、その前後の動作も確認

**経験豊富なオペレーターでも**:
- **毎回ドライランを実施**することを推奨
- 「いつも大丈夫」という油断が事故につながる
- 安全は習慣化することが重要

**プログラムの検証チェックリスト**:
- [ ] 単位（G20/G21）が正しいか
- [ ] 座標系（G54-G59/G92）が正しいか
- [ ] Z軸の深さ設定が適切か
- [ ] 工具径補正（G40/G41/G42）が正しいか
- [ ] 送り速度が適切か
- [ ] 主軸回転数が適切か
- [ ] ドライランで動作確認済みか

:::

### 4.5 基本的なG-codeプログラム例

```gcode
%                    ; プログラム開始
O1000                ; プログラム番号
G21                  ; メートル単位
G17                  ; XY平面選択
G90                  ; 絶対座標
G54                  ; ワーク座標系選択
G00 X0 Y0            ; 原点に移動（位置決め）
M03 S1000            ; 主軸正転、回転数1000rpm
G43 H01 Z10          ; 工具長補正、Z=10mmに移動
G01 Z-5 F100         ; Z=-5mmまで切削送り（送り速度100mm/min）
G01 X10 Y10 F200     ; (10, 10)まで直線切削
G02 X20 Y10 I5 J0    ; 時計回り円弧（中心は(15, 10)、半径5mm）
G01 X20 Y0           ; (20, 0)まで直線切削
G00 Z10              ; Z=10mmまで位置決め
M05                  ; 主軸停止
M30                  ; プログラム終了
%
```

## 5. 曲線とG-code：詳細解説

### 5.1 円弧補間（G02/G03）の詳細

#### 5.1.1 基本概念

**G02（時計回り円弧補間）**と**G03（反時計回り円弧補間）**は、工具を円弧状に移動させるG-code命令です。

**方向の定義**:
- **G02**: 時計回り（Clockwise）
- **G03**: 反時計回り（Counterclockwise）

**平面の選択**:
- **G17**: XY平面（I、Jを使用）
- **G18**: XZ平面（I、Kを使用）
- **G19**: YZ平面（J、Kを使用）

#### 5.1.2 IJK形式（中心オフセット形式）

**構文**:
```gcode
G02 X終点 Y終点 I中心オフセットX J中心オフセットY F送り速度
G03 X終点 Y終点 I中心オフセットX J中心オフセットY F送り速度
```

**特徴**:
- **I、J、K**: 始点から中心点への**オフセット**（増分値）
  - I: X軸方向のオフセット
  - J: Y軸方向のオフセット
  - K: Z軸方向のオフセット
- **明確性**: 中心点が明示的に指定されるため、曖昧さがない
- **180度以上の円弧**: 完全にサポート
- **全円**: 完全にサポート

**例**:
```gcode
; 始点(0, 0)から終点(10, 0)へ、中心(5, 5)を通る時計回り円弧
G02 X10 Y0 I5 J5 F200

; XY平面で、始点(0, 0)から終点(0, 10)へ、中心(5, 5)を通る反時計回り円弧
G17                  ; XY平面選択
G03 X0 Y10 I5 J5 F200
```

**計算方法**:
- 始点: (X_start, Y_start)
- 中心点: (X_start + I, Y_start + J)
- 終点: (X_end, Y_end)

#### 5.1.3 R形式（半径形式）

**構文**:
```gcode
G02 X終点 Y終点 R半径 F送り速度
G03 X終点 Y終点 R半径 F送り速度
```

**特徴**:
- **R**: 円弧の**半径**（単一の値）
- **簡潔性**: 記述が短く、読みやすい
- **制限**: 
  - 180度以上の円弧は曖昧になる可能性がある
  - 全円はサポートされない、または曖昧

**180度以上の円弧の扱い**:
- 一部のコントローラーでは、**正のR**（R>0）で180度以下の円弧、**負のR**（R<0）で180度以上の円弧を指定
- しかし、この動作はコントローラーによって異なる

**例**:
```gcode
; 始点(0, 0)から終点(10, 0)へ、半径5mmの時計回り円弧（180度以下）
G02 X10 Y0 R5 F200

; 180度以上の円弧（コントローラーによって動作が異なる）
G02 X10 Y0 R-5 F200  ; 一部のコントローラーでは180度以上の円弧
```

#### 5.1.4 IJK形式 vs R形式の比較

| 特徴 | IJK形式 | R形式 |
| :--- | :--- | :--- |
| **明確性** | ✅ 非常に明確（中心点が明示的） | ⚠️ 180度以上で曖昧になる可能性 |
| **全円** | ✅ 完全にサポート | ❌ サポートされない、または曖昧 |
| **180度以上の円弧** | ✅ 完全にサポート | ⚠️ コントローラー依存（負のRを使用） |
| **記述の簡潔性** | ❌ オフセット計算が必要 | ✅ シンプルで読みやすい |
| **精度** | ✅ 高精度 | ✅ 高精度（180度以下） |
| **推奨用途** | 全円、180度以上の円弧、高精度が必要な場合 | 180度以下の単純な円弧 |

**推奨**:
- **180度以下の円弧**: R形式でも問題なし（簡潔で読みやすい）
- **180度以上の円弧**: IJK形式を推奨（明確性のため）
- **全円**: IJK形式を必須（R形式では不可能）

#### 5.1.5 実際の変換例

**DXF ARCエンティティからG-codeへの変換**:

```python
def dxf_arc_to_gcode(arc_entity, start_point, plane='XY'):
    """DXF ARCエンティティをG-codeに変換"""
    center = arc_entity.dxf.center
    radius = arc_entity.dxf.radius
    start_angle = arc_entity.dxf.start_angle  # 度
    end_angle = arc_entity.dxf.end_angle      # 度
    
    # 終点を計算
    import math
    end_x = center.x + radius * math.cos(math.radians(end_angle))
    end_y = center.y + radius * math.sin(math.radians(end_angle))
    
    # 中心オフセットを計算
    i_offset = center.x - start_point[0]
    j_offset = center.y - start_point[1]
    
    # 角度差を計算
    angle_diff = end_angle - start_angle
    if angle_diff < 0:
        angle_diff += 360
    
    # 時計回りか反時計回りかを判定
    if angle_diff <= 180:
        gcode = f"G02 X{end_x:.3f} Y{end_y:.3f} I{i_offset:.3f} J{j_offset:.3f}"
    else:
        gcode = f"G03 X{end_x:.3f} Y{end_y:.3f} I{i_offset:.3f} J{j_offset:.3f}"
    
    return gcode

# 使用例
# DXF ARC: 中心(5, 5), 半径5, 開始角度0度, 終了角度90度
# 始点: (10, 5)
gcode = dxf_arc_to_gcode(arc_entity, (10, 5))
# 出力: G03 X5.000 Y10.000 I-5.000 J0.000
```

### 5.2 SPLINEのG-codeへの変換

#### 5.2.1 変換の必要性

**問題**: ほとんどのCNCコントローラーは、SPLINEエンティティを直接処理できません。

**解決策**: SPLINEを**点列に近似**して、複数の`G01`（線形補間）命令に変換します。

#### 5.2.2 許容誤差（Tolerance）の概念

**弦誤差（Chord Error）**:
- 曲線上の点と、それを結ぶ直線（弦）との間の**最大距離**
- この誤差が小さいほど、曲線の近似精度が高い

**許容誤差の設定**:
- **粗加工**: 0.05-0.1mm程度（緩い許容誤差）
- **中程度の精度**: 0.01-0.05mm程度
- **仕上げ加工**: 0.001-0.01mm程度（厳しい許容誤差）

#### 5.2.3 変換アルゴリズム

**基本的なアプローチ**:

1. **均等分割**:
   - 曲線を均等なパラメータ間隔で分割
   - シンプルだが、曲率が高い部分で精度が低下

2. **適応的分割**（推奨）:
   - 曲率に応じて分割密度を調整
   - 曲率が高い部分では細かく分割、低い部分では粗く分割
   - より効率的で精度が高い

**実装例**:

```python
import ezdxf
from ezdxf.math import BSpline
import math

def spline_to_gcode_adaptive(spline_entity, tolerance=0.01, max_segments=1000):
    """SPLINEを適応的分割でG-codeに変換"""
    # BSplineオブジェクトを作成
    bspline = BSpline(
        spline_entity.control_points,
        order=spline_entity.dxf.degree + 1,
        knots=spline_entity.knots
    )
    
    gcode_lines = []
    t = 0.0
    t_end = 1.0
    current_point = bspline.point(t)
    
    # 最初の点に移動
    gcode_lines.append(f"G01 X{current_point.x:.3f} Y{current_point.y:.3f} F200")
    
    segment_count = 0
    while t < t_end and segment_count < max_segments:
        # 次の点を試行
        t_next = min(t + 0.1, t_end)  # 初期ステップ
        next_point = bspline.point(t_next)
        
        # 弦誤差を計算
        chord_error = calculate_chord_error(bspline, t, t_next)
        
        # 許容誤差内なら採用、そうでなければステップを小さく
        if chord_error <= tolerance:
            # 許容誤差内なので採用
            gcode_lines.append(f"G01 X{next_point.x:.3f} Y{next_point.y:.3f} F200")
            t = t_next
            current_point = next_point
            segment_count += 1
        else:
            # ステップを小さくして再試行
            t_next = t + (t_next - t) * 0.5
    
    return "\n".join(gcode_lines)

def calculate_chord_error(bspline, t1, t2):
    """2点間の弦誤差を計算（簡略化した実装）"""
    p1 = bspline.point(t1)
    p2 = bspline.point(t2)
    t_mid = (t1 + t2) / 2
    p_mid = bspline.point(t_mid)
    
    # 弦の中点と曲線上の点の距離を計算
    chord_mid = ((p1.x + p2.x) / 2, (p1.y + p2.y) / 2)
    error = math.sqrt((p_mid.x - chord_mid[0])**2 + (p_mid.y - chord_mid[1])**2)
    
    return error
```

#### 5.2.4 円弧フィッティング（Arc Fitting）

**概念**:
- 点列を生成した後、連続する3点が円弧に適合する場合は、`G02`または`G03`を使用
- G-codeのサイズを削減し、加工も滑らかになる

**アルゴリズム**:
1. 点列を生成
2. 連続する3点をチェック
3. 3点が円弧に適合する場合、`G02`または`G03`に変換
4. 適合しない場合、`G01`のまま

**実装例**:

```python
def points_to_gcode_with_arc_fitting(points, arc_tolerance=0.01):
    """点列をG-codeに変換（円弧フィッティング付き）"""
    gcode_lines = []
    i = 0
    
    while i < len(points):
        if i + 2 < len(points):
            # 3点で円弧を試行
            p1, p2, p3 = points[i], points[i+1], points[i+2]
            
            # 3点から円弧を計算
            arc_params = fit_arc_to_three_points(p1, p2, p3)
            
            if arc_params and arc_params['error'] <= arc_tolerance:
                # 円弧として出力
                center, radius, start_angle, end_angle = arc_params['params']
                i_offset = center[0] - p1[0]
                j_offset = center[1] - p1[1]
                
                # 時計回りか反時計回りかを判定
                if end_angle > start_angle:
                    gcode_lines.append(f"G02 X{p3[0]:.3f} Y{p3[1]:.3f} I{i_offset:.3f} J{j_offset:.3f} F200")
                else:
                    gcode_lines.append(f"G03 X{p3[0]:.3f} Y{p3[1]:.3f} I{i_offset:.3f} J{j_offset:.3f} F200")
                
                i += 2  # 2点スキップ（次の点から再開）
            else:
                # 線形補間
                gcode_lines.append(f"G01 X{p2[0]:.3f} Y{p2[1]:.3f} F200")
                i += 1
        else:
            # 残りの点は線形補間
            gcode_lines.append(f"G01 X{points[i][0]:.3f} Y{points[i][1]:.3f} F200")
            i += 1
    
    return "\n".join(gcode_lines)
```

#### 5.2.5 許容誤差の選択指針

**一般的な指針**:

| 用途 | 推奨許容誤差 | 理由 |
| :--- | :--- | :--- |
| **粗加工** | 0.05-0.1mm | 仕上げ加工で修正されるため、緩い許容誤差で問題なし |
| **中程度の精度** | 0.01-0.05mm | 一般的な機械部品の精度要件 |
| **仕上げ加工** | 0.001-0.01mm | 表面仕上げや形状精度が重要な場合 |
| **光学部品、金型** | ≤0.01mm | 非常に高い精度が必要 |

**計算式**:
- 許容誤差は、**曲線の半径の0.001-0.005倍**程度を目安とする
- 例：半径10mmの曲線の場合、0.01-0.05mm程度の許容誤差が適切

**トレードオフ**:
- **厳しい許容誤差**: 点の数が増え、G-codeが長くなる、処理が遅くなる
- **緩い許容誤差**: G-codeが短くなるが、曲線の精度が低下、表面が粗くなる

### 5.4 変換時の注意点とベストプラクティス

#### 5.4.1 コントローラー依存の動作

**IJK形式の座標モード**:
- **G90（絶対座標）**: 終点は絶対座標、IJKオフセットは始点からの増分
- **G91（増分座標）**: 終点も増分座標、IJKオフセットも増分

**R形式の符号**:
- 一部のコントローラーでは、**正のR**で180度以下、**負のR**で180度以上
- しかし、この動作はコントローラーによって異なる
- **推奨**: 180度以上の円弧はIJK形式を使用

#### 5.4.2 精度とパフォーマンスのバランス

**許容誤差の選択**:
- 加工精度とG-codeサイズのバランスを考慮
- テストカットで実際の精度を確認

**データストレベーション（Data Starvation）**:
- 許容誤差が厳しすぎると、G-codeブロックが多くなり、コントローラーが処理しきれなくなる可能性がある
- 特に古いコントローラーでは注意が必要

**円弧フィッティングの活用**:
- 可能な限り円弧フィッティングを使用して、G-codeサイズを削減
- 加工も滑らかになる

#### 5.4.3 実用的な推奨事項

1. **180度以下の円弧**: R形式を使用（簡潔で読みやすい）
2. **180度以上の円弧**: IJK形式を使用（明確性のため）
3. **全円**: IJK形式を必須
4. **SPLINE変換**: 適応的分割を使用し、許容誤差を適切に設定
5. **円弧フィッティング**: 可能な限り使用してG-codeサイズを削減
6. **テスト**: 実際の加工前にシミュレーターで確認

## 6. DXFからG-codeへの変換

### 6.1 変換プロセス

DXFファイルからG-codeを生成するには、**CAMソフト**（Computer-Aided Manufacturing）が必要です。

**変換の流れ**:
1. **DXFファイルの読み込み**: CAMソフトがDXFファイルを読み込む
2. **工具パスの生成**: 工具の動きを計算
3. **工具径補正**: 工具の直径を考慮してパスを補正
4. **G-codeの生成**: 計算されたパスをG-codeに変換
5. **ポストプロセッサー**: 特定のCNCコントローラー用にG-codeを調整

### 6.2 変換時の注意点

**エンティティの変換**:
- **LINE**: `G01`（線形補間）に変換
- **ARC**: `G02`または`G03`（円弧補間）に変換
- **CIRCLE**: `G02`または`G03`で円を描く
- **LWPOLYLINE**: 複数の`G01`に変換、または円弧部分は`G02/G03`に変換
- **SPLINE**: 多数の`G01`に変換（点列に近似）、または円弧フィッティングを使用

**精度の設定**:
- SPLINEを点列に変換する際の許容誤差を設定
- 許容誤差が小さいほど、点の数が増え、G-codeが長くなる

**ポストプロセッサーの選択**:
- 使用するCNCコントローラー（Fanuc、Siemens、Heidenhain等）に合わせたポストプロセッサーを選択
- 間違ったポストプロセッサーを使用すると、G-codeが正しく実行されない

## 7. 3DプリンターとG-code：なぜ同じ言語が使えるのか？

### 7.1 基本的な共通点

**重要な事実**: 3DプリンターとCNC工作機械は、**同じG-code言語を使用しています**が、それぞれに特有の拡張機能があります。

**共通する理由**:
1. **幾何学的な動きの制御**: どちらもX、Y、Z軸の精密な移動が必要
2. **標準化の利点**: 既存のソフトウェアやツールが利用できる
3. **拡張性**: G-codeのモジュラー設計により、各用途に合わせて拡張可能

### 7.2 3Dプリンター特有の拡張機能

#### 7.2.1 温度制御コマンド

3Dプリンターは、材料を溶かして積層するため、**温度制御**が重要です。

| Mコード | 機能 | 説明 |
| :--- | :--- | :--- |
| **M104** | エクストルーダー温度設定（非ブロッキング） | 目標温度を設定するが、待機しない |
| **M109** | エクストルーダー温度設定（ブロッキング） | 目標温度に達するまで待機 |
| **M140** | ヒートベッド温度設定（非ブロッキング） | ベッドの目標温度を設定するが、待機しない |
| **M190** | ヒートベッド温度設定（ブロッキング） | ベッドが目標温度に達するまで待機 |
| **M105** | 温度読み取り | 現在の温度を読み取る |

**使用例**:
```gcode
; プリント開始時の典型的なシーケンス
M140 S60          ; ベッドを60度に加熱開始（待機しない）
M104 S200         ; エクストルーダーを200度に加熱開始（待機しない）
M190 S60          ; ベッドが60度になるまで待機
M109 S200         ; エクストルーダーが200度になるまで待機
; これにより、ベッドとエクストルーダーを同時に加熱して時間を節約
```

#### 7.2.2 エクストルーダー制御（E軸）

3Dプリンターは、**E軸（Extruder軸）**を使用して材料の押し出し量を制御します。

**特徴**:
- E軸は、移動距離に応じた材料の押し出し量を指定
- 通常は絶対値（累積値）で指定される
- リトラクション（材料の引き戻し）もE軸で制御

**使用例**:
```gcode
G1 X10 Y10 E5.0 F200    ; (10, 10)に移動し、5mm分の材料を押し出す
G1 X20 Y10 E10.0        ; (20, 10)に移動し、さらに5mm分の材料を押し出す（累積10mm）
G1 E8.0                 ; 材料を2mm引き戻す（リトラクション）
```

#### 7.2.3 ファン制御

3Dプリンターは、材料の冷却のために**ファン**を使用します。

| Mコード | 機能 | 説明 |
| :--- | :--- | :--- |
| **M106** | ファン速度設定 | ファンの速度を設定（0-255） |
| **M107** | ファンOFF | ファンを停止 |

**使用例**:
```gcode
M106 S255    ; ファンを最大速度で回転
M106 S128    ; ファンを50%の速度で回転
M107         ; ファンを停止
```

#### 7.2.4 その他の3Dプリンター特有のコマンド

| コマンド | 機能 | 説明 |
| :--- | :--- | :--- |
| **G28** | ホーミング | すべての軸を原点に移動 |
| **G29** | ベッドレベル調整 | 自動ベッドレベル調整を実行 |
| **G92** | 位置設定 | 現在位置を指定した値に設定 |
| **M82** | エクストルーダー絶対モード | E軸を絶対座標モードに設定 |
| **M83** | エクストルーダー増分モード | E軸を増分座標モードに設定 |

### 7.3 CNC工作機械との違い

#### 7.3.1 主な違いの比較

| 特徴 | CNC工作機械 | 3Dプリンター |
| :--- | :--- | :--- |
| **主な操作** | 減算加工（材料を削る） | 加算加工（材料を積層） |
| **工具制御** | 主軸回転（M03/M04/M05）、工具交換（M06） | エクストルーダー温度（M104/M109）、材料押し出し（E軸） |
| **冷却** | 冷却液（M07/M08/M09） | 冷却ファン（M106/M107） |
| **円弧補間** | G02/G03を頻繁に使用 | G02/G03のサポートは限定的、多くのスライサーはG01のみを出力 |
| **モーダル動作** | 強力（G90/G91、G17/G18/G19等が有効なまま） | 弱い（多くのコマンドが絶対的） |
| **ワーク座標系** | G54-G59で複数のワーク座標系をサポート | 限定的なサポート（G92等） |
| **工具径補正** | G40/G41/G42で工具径を補正 | 不要（材料を押し出すため） |

#### 7.3.2 円弧補間の違い

**CNC工作機械**:
- G02/G03を頻繁に使用
- 円弧補間が標準機能

**3Dプリンター**:
- **多くのスライサーはG01のみを出力**
- 理由：STLファイル（3Dモデル）は三角形メッシュで表現されるため、曲線が既に線分に分割されている
- MarlinファームウェアはG02/G03をサポートしているが、多くの場合コンパイル時に無効化されている（メモリ節約のため）

**実例**:
```gcode
; CNC工作機械（円弧補間を使用）
G02 X10 Y0 I5 J0 F200    ; 円弧補間

; 3Dプリンター（多くのスライサーは線分に分割）
G1 X1.0 Y0.0 E0.1
G1 X2.0 Y0.1 E0.2
G1 X3.0 Y0.3 E0.3
...                      ; 多数のG01命令で円弧を近似
```

### 7.4 なぜ同じG-codeが使えるのか？

#### 7.4.1 幾何学的な動きの制御が共通

**核心的な理由**: どちらも**「工具（またはノズル）を3次元空間で正確に移動させる」**必要があるため、G-codeの基本的な動き制御コマンド（G00、G01、G02、G03等）が共通して使用できます。

**共通する要素**:
- X、Y、Z軸の移動
- 送り速度（F）の制御
- 座標系の管理

#### 7.4.2 標準化の利点

**既存のインフラの活用**:
- CAD/CAMソフトウェアが既にG-codeをサポート
- 3DプリンターのスライサーもG-codeを出力
- 既存のツールや知識を再利用できる

**拡張性**:
- G-codeのモジュラー設計により、各用途に合わせて拡張可能
- CNC工作機械は主軸制御を追加
- 3Dプリンターは温度制御とエクストルーダー制御を追加

#### 7.4.3 歴史的な経緯

**G-codeの起源**:
- 1960年代にCNC工作機械のために開発
- 1980年代にRS-274-Dとして標準化
- 1990年代以降、3Dプリンター（RepRapプロジェクト）がG-codeを採用

**3DプリンターがG-codeを採用した理由**:
- 既存の標準を活用することで、開発コストを削減
- CNC工作機械の知識を3Dプリンターに応用可能
- 既存のソフトウェアツールを利用可能

### 7.5 3Dプリンター用G-codeの特徴

#### 7.5.1 スライサーによる生成

**スライサーソフトウェア**:
- Cura、PrusaSlicer、Simplify3D等が、3Dモデル（STL等）からG-codeを生成
- レイヤーごとにパスを計算
- 温度、ファン、リトラクションなどの設定をG-codeに埋め込む

**典型的なG-codeファイルの構造**:
```gcode
; 開始スクリプト
M140 S60          ; ベッド温度設定
M104 S200         ; エクストルーダー温度設定
G28               ; ホーミング
G29               ; ベッドレベル調整
G1 Z0.2 F3000     ; Z軸を0.2mmに移動
M109 S200         ; エクストルーダーが200度になるまで待機
M190 S60          ; ベッドが60度になるまで待機

; レイヤー1
G1 X10 Y10 Z0.2 E5.0 F200
G1 X20 Y10 E10.0
...

; レイヤー2
G1 X10 Y10 Z0.4 E15.0
...

; 終了スクリプト
M104 S0           ; エクストルーダーを冷却
M140 S0           ; ベッドを冷却
M107              ; ファンを停止
G28 X Y           ; X、Y軸をホーミング
```

#### 7.5.2 モーダル動作の違い

**CNC工作機械**:
- モーダル動作が強力
- G90（絶対座標）を設定すると、変更されるまで有効

**3Dプリンター（Marlin等）**:
- モーダル動作が弱い
- 多くのコマンドが絶対的
- 1行に複数のコマンドを書くことは一般的ではない

**例**:
```gcode
; CNC工作機械（モーダル動作）
G90               ; 絶対座標モード
G1 X10 Y10        ; 絶対座標(10, 10)に移動
G1 X20 Y20        ; 絶対座標(20, 20)に移動（G90が有効なまま）

; 3Dプリンター（多くの場合、明示的に指定）
G1 X10 Y10 E5.0   ; 絶対座標(10, 10)に移動、材料5mm押し出し
G1 X20 Y20 E10.0  ; 絶対座標(20, 20)に移動、材料10mm押し出し（累積）
```

### 7.6 互換性の問題

#### 7.6.1 CNC用G-codeを3Dプリンターで実行する場合

**問題**:
- 主軸制御コマンド（M03/M04/M05）が無意味
- 冷却液コマンド（M07/M08/M09）が無意味
- 工具交換コマンド（M06）が無意味
- エクストルーダー制御がないため、材料が押し出されない

**結果**:
- 3Dプリンターは、理解できないコマンドを無視するか、エラーを出す
- 材料が押し出されないため、プリントが失敗する

#### 7.6.2 3Dプリンター用G-codeをCNC工作機械で実行する場合

**問題**:
- 温度制御コマンド（M104/M109/M140/M190）が無意味
- エクストルーダー制御（E軸）が無意味
- ファン制御（M106/M107）が無意味

**結果**:
- CNC工作機械は、理解できないコマンドを無視する
- 工具が動くが、切削は行われない（工具が材料に接触しない）

### 7.7 まとめ：3DプリンターとCNC工作機械のG-code

**共通点**:
- ✅ 基本的な動き制御コマンド（G00、G01、G02、G03等）は共通
- ✅ X、Y、Z軸の移動は同じ
- ✅ 送り速度（F）の制御は同じ

**違い**:
- ❌ 3Dプリンターは温度制御とエクストルーダー制御を追加
- ❌ CNC工作機械は主軸制御と工具制御を追加
- ❌ 3Dプリンターは円弧補間の使用が限定的
- ❌ モーダル動作の強さが異なる

**なぜ同じG-codeが使えるのか**:
1. **幾何学的な動きの制御が共通**: どちらも3次元空間での精密な移動が必要
2. **標準化の利点**: 既存のソフトウェアやツールを活用できる
3. **拡張性**: G-codeのモジュラー設計により、各用途に合わせて拡張可能
4. **歴史的な経緯**: 3Dプリンターが既存のG-code標準を採用した

**実用的な推奨事項**:
- CNC用G-codeと3Dプリンター用G-codeは**互換性がない**
- それぞれの用途に合わせたG-codeを使用する必要がある
- スライサーやCAMソフトが、適切なG-codeを生成する

## 8. 実用的な推奨事項

### 8.1 安全面の推奨事項（最重要）

::: warning ⚠️ 安全第一：G-codeは物理的な機械を動かします

**必須の安全対策**:
1. **ドライラン（空運転）の実施**: 新しいプログラムや変更したプログラムは、必ずドライランで動作確認
2. **シミュレーターの使用**: CAMソフトのシミュレーター機能で、工具パスを事前に確認
3. **段階的な実行**: 最初は低い送り速度で実行し、問題がないことを確認してから本番速度に上げる
4. **緊急停止ボタンの確認**: 常に緊急停止ボタンの位置を確認し、すぐに押せる状態にする
5. **座標系の確認**: G54-G59やG92の設定が正しいか、必ず確認

詳細は[4.4 安全面への警告](#44-安全面への警告g-codeは物理的な機械を動かします)を参照してください。

:::

### 8.2 互換性を確保するために

1. **正しいポストプロセッサーを使用**:
   - CAMソフトで、使用するCNCコントローラー用のポストプロセッサーを選択
   - 間違ったポストは、正しく動作しないG-codeを生成する可能性がある

2. **テストとシミュレーション**:
   - 実際の加工前に、シミュレーターや**ドライラン（空運転）**で動作を確認
   - 特に固定サイクル、工具交換、サブプログラムの動作を確認
   - **安全面の観点からも、ドライランは必須**

3. **変換時の注意**:
   - Fanuc用のプログラムをHeidenhainで実行する場合、サイクル構文や変数の変換が必要
   - ブロックごとに慎重に確認

4. **ベンダードキュメントの参照**:
   - 各メーカーは詳細なコードマニュアルを提供
   - コントローラー固有の違いを確認

5. **プログラムにコントローラー種別を記載**:
   - プログラムの先頭（コメント）に、どのコントローラー用かを記載
   - 複数ブランドの機械がある場合、ディレクトリやバックアップを分ける

### 8.3 DXFからG-codeへの変換時の推奨事項

1. **DXFファイルの準備**:
   - SPLINEをLWPOLYLINEに変換（加工機の互換性のため）
   - 不要なエンティティ（TEXT、MTEXT等）を削除
   - 閉じたループを確認

2. **CAMソフトの設定**:
   - 工具径、切削速度、送り速度を適切に設定
   - 許容誤差を設定（SPLINE変換時）

3. **ポストプロセッサーの選択**:
   - 使用するCNCコントローラーに合わせたポストプロセッサーを選択
   - 必要に応じて、ポストプロセッサーをカスタマイズ

## 9. G-codeの問題点と後継標準

### 9.1 G-codeの主要な問題点

G-code（ISO 6983 / RS-274-D）は、50年以上にわたって使用されてきましたが、現代の製造業の要求に対して以下のような問題点があります。

#### 9.1.1 意味情報の欠如

**問題**: G-codeは、**「どのように動かすか」**しか表現できず、**「何を加工しているか」**という意味情報を持たない。

**具体例**:
- 穴、ポケット、面などの**加工特徴（Feature）**の情報がない
- **寸法公差や幾何公差（GD&T）**の情報がない
- **材料情報**がない
- **工具情報**が限定的

**影響**:
- 工具パスがポストプロセッサー時点で固定され、柔軟性が低い
- 設計意図が製造段階で失われる
- 検証やトレーサビリティが困難

#### 9.1.2 ベンダー方言による分断

**問題**: 各CNCメーカーが独自の拡張機能を追加し、**互換性が失われている**。

**具体例**:
- Fanuc、Siemens、Heidenhainなど、それぞれ異なるG-code方言
- 同じ標準をベースにしていても、プログラムをそのまま移植できない
- CAMソフトは、各メーカー用のポストプロセッサーを多数用意する必要がある

**影響**:
- ポストプロセッサーの開発・保守コストが高い
- エラーが発生しやすい
- 機械間でのプログラムの移植が困難

#### 9.1.3 可搬性と機械依存性の問題

**問題**: G-codeファイルは、**特定の機械の動力学や軸構成に依存**している。

**具体例**:
- 機械の軸構成（3軸、4軸、5軸等）に依存
- 機械の制限（ストローク、速度等）に依存
- 工具の種類やサイズに依存

**影響**:
- 異なる機械間でプログラムを移植する際に、大幅な修正が必要
- 工具の変更時に、プログラム全体の見直しが必要
- 機械の更新時に、既存プログラムの互換性が失われる

#### 9.1.4 複雑な操作への対応不足

**問題**: 5軸加工、適応的工具パス、オンライン計測、リアルタイムフィードバックなどの**高度な操作に対応しにくい**。

**具体例**:
- 5軸加工の複雑な工具姿勢制御が困難
- 特徴ベースの適応的工具パスが実現困難
- 条件分岐やループなどの制御構造が限定的
- リアルタイムフィードバックとの統合が困難

**影響**:
- 高度な加工が困難
- 加工効率の向上が限定的
- 自動化の進展が遅い

#### 9.1.5 設計情報の欠落

**問題**: CAD/CAMの幾何情報、寸法公差、治具、素材、工具データが**G-codeに正式に含まれない**。

**具体例**:
- 設計意図（どの特徴を加工するか）が失われる
- 寸法公差の情報が失われる
- 治具の情報が失われる
- 素材の情報が失われる

**影響**:
- 設計意図と製造結果の不一致が発生しやすい
- 品質管理が困難
- トレーサビリティが低い

#### 9.1.6 保守・検証・トレーサビリティの課題

**問題**: G-codeは低レベルなため、**手動レビューが困難で、エラーが発生しやすい**。

**具体例**:
- 単位の間違い（インチ vs ミリメートル）
- オフセットの欠落
- 座標の混同
- 構文エラー

**影響**:
- エラーが発生しやすい
- デバッグが困難
- どの特徴がどの工具パスに対応するかの追跡が困難
- 品質保証が困難

### 9.2 STEP-NC：G-codeの後継標準

#### 9.2.1 STEP-NCとは

**STEP-NC**は、G-codeの限界を克服するために開発された、**次世代のCNC制御言語/標準**です。

**正式名称**:
- **ISO 14649**: 加工制御のためのデータモデル
- **ISO 10303-238 (AP-238)**: STEP（ISO 10303）との統合、より高度な機能

**主な特徴**:
- **特徴ベース**: 加工特徴（穴、ポケット等）を直接表現
- **機械独立**: 工具中心プログラミング、抽象的操作
- **統合データ**: 幾何情報、寸法公差、工具情報、治具情報を1つのファイルに統合
- **高レベル**: 低レベルの軸移動ではなく、高レベルの操作を表現

#### 9.2.2 STEP-NCのバージョン

| バージョン | 年 | 主な特徴 |
| :--- | :--- | :--- |
| **AP-238 Edition 1** | 2007年 | 最初のバージョン |
| **AP-238 Edition 2** | 2020年 | 機能拡張 |
| **AP-238 Edition 3** | 2022年 | ハイブリッド製造、機械動力学、GD&T、デジタルツインサポート |
| **AP-238 Edition 4** | 検討中 | より詳細なAM（付加製造）サポート |

**ISO 14649-17（2020年）**:
- 付加製造（3Dプリンター等）のための標準
- ただし、FDM、LMDなどの特定技術のサポートが不足

#### 9.2.3 STEP-NCがG-codeの問題をどう解決するか

| G-codeの問題 | STEP-NCの解決策 |
| :--- | :--- |
| **低レベルの移動のみ** | 抽象的操作、特徴認識、機械独立 |
| **方言の非互換性** | 統一されたEXPRESSスキーマ、標準準拠クラス |
| **機械間の移植困難** | 機械モデル、工具情報を含む記述、システムが工具パスを適応 |
| **設計/公差/文脈データの欠落** | 幾何、公差、素材、治具を1つのファイルに統合 |
| **トレーサビリティの低さ** | より豊富なメタデータ、文脈情報、シミュレーション/検証機能 |

**具体例**:

**G-codeの場合**:
```gcode
G00 X10 Y10 Z5
G01 Z-5 F100
G01 X20 Y10
G01 X20 Y20
G01 X10 Y20
G01 X10 Y10
G00 Z5
```
→ これは「何を加工しているか」が不明（ポケット？外形？）

**STEP-NCの場合**:
```xml
<workingstep>
  <feature>pocket</feature>
  <depth>5mm</depth>
  <tolerance>±0.01mm</tolerance>
  <tool>endmill_10mm</tool>
  <material>aluminum</material>
</workingstep>
```
→ 「10mmエンドミルでアルミニウムのポケットを5mm深さ、±0.01mmの公差で加工する」という意味情報を含む

### 9.3 STEP-NCの採用状況と課題

#### 9.3.1 採用状況（2024-2025年時点）

**研究・プロトタイプ段階**:
- ✅ 研究機関や大学での実証実験が行われている
- ✅ 5軸加工、Boeing/NISTの可搬性テスト、Toulouseでの実証実験など
- ✅ エッジ/クラウド協調製造システムのプロトタイプ

**産業界での採用**:
- ⚠️ **限定的**: 主要なCNCメーカーやCAM/CNCプラットフォームでの本格的な採用は少ない
- ⚠️ **実験的**: ラボ規模のテストリグや小規模ワークショップでの実装
- ⚠️ **パイロットプロジェクト**: 航空宇宙、医療などの特定業界でのパイロットプロジェクト

**現状**:
- 多くの工場では、**G-codeが依然として標準**
- STEP-NCは、G-codeベースのワークフローを**補完・拡張**する形で使用されることが多い
- G-codeからSTEP-NCへの変換ツールも開発されているが、本格的な生産環境での使用は限定的

#### 9.3.2 採用が進まない理由

**1. ベンダーサポートの不足**
- 多くのCNCコントローラーがSTEP-NCを完全にサポートしていない
- 既存のG-codeベースのインフラが広く普及している
- ハードウェアとソフトウェアの更新コストが高い

**2. データの複雑さと処理負荷**
- STEP-NCファイルは大きく、複雑
- パース、シミュレーション、エラー検出に多くのリソースが必要
- 一部の機械コントローラーは計算能力が限られている

**3. 特徴認識と意味抽出の負担**
- 基本ツールパスを超える準拠クラスには、適切な特徴定義が必要
- CAD/CAMが特徴を生成または推論する必要があり、負担が増加

**4. 経済的・教育的障壁**
- 特に中小企業（SME）では、資金、専門知識、インセンティブが不足
- 既存のG-codeプログラムの移行、人員の訓練、システムの再構築が必要

**5. 技術固有のサポート不足**
- 付加製造（AM）のサポートが不十分（FDM、LMD等の詳細エンティティが不足）
- 特定の加工方法への対応が限定的

#### 9.3.3 STEP-NCの利点（研究・実証実験での確認）

**性能向上**:
- **加工時間の削減**: AP-238標準により、最適化と自動フィードバック/補償により、**約15%の加工時間削減**が報告されている
- **精度向上**: より豊富な情報により、加工精度が向上
- **相互運用性の向上**: 異なるシステム間でのデータ交換が容易

**その他の利点**:
- モデルベース検査のサポート
- デジタルツイン/デジタルスレッドとの統合
- トレーサビリティの向上

### 9.4 将来の展望（2025-2026年以降）

#### 9.4.1 標準の拡張

**付加製造（AM）への拡張**:
- ISO 14649-17の拡張が検討されている
- FDM、PBF（粉末床溶融）、LMDなどの特定技術の詳細エンティティが追加される予定
- AP-238 Edition 4に含まれる可能性

**デジタルツイン/デジタルスレッドとの統合**:
- ISO 23247（デジタルツイン）との統合
- OPC-UA、MQTT、QIFなどの標準との統合
- Industry 4.0 / Industry 5.0エコシステムの一部として

#### 9.4.2 採用の見通し

**短期（1-3年）**:
- 研究機関や大学での実証実験の継続
- 特定業界（航空宇宙、医療等）でのパイロットプロジェクトの増加
- 教育機関での導入

**中期（3-5年）**:
- より多くのCNCコントローラーがSTEP-NCをサポート
- 中小企業への普及が始まる可能性
- G-codeとの併用が一般的

**長期（5-10年）**:
- STEP-NCが主流になる可能性
- ただし、G-codeは完全には置き換えられない可能性（レガシーシステムとの互換性のため）

### 9.5 STEP-NCは真の後継なのか？

#### 9.5.1 標準の観点から

**はい、後継標準です**:
- ISO 10303-238 (AP-238)は、**正式にG-code（ISO 6983）の後継**として設計されている
- 長期的にはG-codeを置き換えることを目指している

#### 9.5.2 実用的な現実

**まだ完全な置き換えではありません**:
- 多くの工場では、**G-codeが依然として標準**
- 既存のコードベース、レガシーマシン、ベンダーサポート、ユーザーの慣れ親しみが大きい
- STEP-NCは、G-codeベースのワークフローを**補完・拡張**する形で使用されることが多い

**実用的なアプローチ**:
- G-codeからSTEP-NCへの変換ツールの開発
- レガシープログラムの再利用
- 段階的な移行戦略

### 9.6 まとめ：G-codeの問題点と後継標準

**G-codeの主要な問題点**:
1. 意味情報の欠如（何を加工しているかが不明）
2. ベンダー方言による分断（互換性の問題）
3. 可搬性と機械依存性の問題
4. 複雑な操作への対応不足
5. 設計情報の欠落
6. 保守・検証・トレーサビリティの課題

**STEP-NC（ISO 14649 / AP-238）**:
- G-codeの問題を解決するために設計された後継標準
- 特徴ベース、機械独立、統合データ、高レベルな操作
- AP-238 Edition 3（2022年）が最新版

**採用状況**:
- 研究・プロトタイプ段階では成功
- 産業界での採用は限定的
- ベンダーサポートの不足、コスト、複雑さが障壁

**将来の展望**:
- 付加製造への拡張が進行中
- デジタルツイン/デジタルスレッドとの統合
- 段階的な採用が予想される

**結論**:
- STEP-NCは**正式な後継標準**だが、**実用的にはまだG-codeが主流**
- 長期的にはSTEP-NCが主流になる可能性があるが、G-codeは完全には置き換えられない可能性がある
- **段階的な移行**が現実的なアプローチ

## 10. まとめ

### G-codeの要点

1. **標準規格**: RS-274-D（EIA）とISO 6983-1:2009が現在の標準
2. **メーカー方言**: Fanuc、Siemens、Heidenhainなど、各メーカーが独自の拡張を追加
3. **互換性**: 標準をベースにしていても、メーカー間で完全な互換性はない
4. **DXFとの関係**: DXFは設計データ、G-codeは加工命令。CAMソフトが変換を担当
5. **3Dプリンター**: 基本的なG-codeは共通だが、温度制御やエクストルーダー制御などの拡張機能がある
6. **問題点**: 意味情報の欠如、ベンダー方言、機械依存性、複雑な操作への対応不足など
7. **後継標準**: STEP-NC（ISO 14649 / AP-238）が開発されているが、産業界での採用は限定的

### 実用的な推奨事項

- **安全第一**: G-codeは物理的な機械を動かすため、必ずドライラン（空運転）で動作確認を実施
- **正しいポストプロセッサーを使用**: CAMソフトで、使用するCNCコントローラー用のポストプロセッサーを選択
- **テストを実施**: 実際の加工前に、シミュレーターやドライランで動作を確認
- **DXFファイルの準備**: 加工機向けにDXFファイルを準備（SPLINEをLWPOLYLINEに変換等）
